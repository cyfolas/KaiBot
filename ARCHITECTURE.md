# Axiom — анализ и целевая архитектура

Документ фиксирует результат аудита проекта (октябрь 2026), целевую архитектуру и модель прав,
к которой приводится сервер, а также проектные решения для планируемых подсистем (голосовые
комнаты, музыка, модерация). Эксплуатационная документация — в `DOCUMENTATION.md`.

---

## 0. Резюме

**Что было.** Небольшой (≈7 300 строк) бот на Serenity 0.12 с продуманным ядром: собственный
слой взаимодействий (`framework`), чистая логика доступа и иерархии с тестами, настройки в
SQLite с единым путём изменения, журналы. Слабые места — не в качестве кода, а в объёме модели:

* бот знал о правах Discord ровно 14 названий из 52 и делил роли на «административные» и
  «остальные» по восьми битам;
* не было ни модели прав сервера, ни средств её проверять и приводить к норме;
* интерфейс — только подкоманды и формы; панелей с меню и страницами не было;
* чистая логика лежала вперемешку с процессной на верхнем уровне `src/`.

**Что сделано в этой итерации.**

| Область | Результат |
|---|---|
| Структура | Чистая логика вынесена в `src/domain/` (`access`, `hierarchy`, `permissions`, `roles`, `policy`, `text`); зависимости направлены строго сверху вниз |
| Права Discord | Каталог всех 52 прав (биты 0–52): русские названия, раздел, типы каналов, уровень опасности; поддержка битов 51–52, которых нет в serenity 0.12 |
| Роли | Классификация `Tier × Origin`: администратор / управление / модерация / доверенные / участники / без прав; обычная / @everyone / интеграция / бусты / подписка / связанная. `/staff` группирует по уровням |
| Политика прав | Модель «@everyone — ничего, участник — права на уровне роли, каналы нейтральны, муты — запреты в каналах»; движок аудит → план → применение с доказанным инвариантом мутов, идемпотентностью и проверкой модели на смоделированном состоянии |
| Интерфейс | Панели: меню выбора ролей, страницы, подтверждение с отпечатком плана; `/perms setup · channel · audit · sync · catalog` |
| Хранение | Миграция `0002_policy.sql`: политика, назначение каналов, роли классов; каскадное удаление |
| Проверка | 102 теста (было 70), `cargo fmt --check`, `clippy -D warnings` |

**Что дальше** — §9: верификация участников и `/mute` поверх политики, голосовые комнаты,
журнал участников, музыка, переход на Components V2 после обновления serenity.

## 1. Аудит исходного состояния

### 1.1. Что сделано хорошо и сохранено

* **Контракт команды** (`SlashCommand`): право, опции и признак «для разработчиков» — данные, из
  которых строится и определение для Discord, и проверка перед каждым шагом. Команда не может
  объявить одно право и забыть проверить другое.
* **Состояние диалога в `custom_id`**: формы и кнопки переживают перезапуск, бот ничего не
  хранит; аргументы перепроверяются на каждом шаге.
* **Защита от «доверенного посредника»**: бот не делает за автора того, что автор не может сам
  (`/say`, `/embed`, `/staff-edit`, журналы).
* **Единый путь изменения настроек**: копия → изменение → транзакция → публикация в памяти.
* **Чистая логика с тестами** там, где она была (`access`, `hierarchy`, журнал сообщений).

### 1.2. Найденные проблемы и решения

| Проблема | Следствие | Решение |
|---|---|---|
| Плоский `src/`: `access.rs`, `hierarchy.rs`, `text.rs` рядом с `app.rs`, `state.rs` | Слои не видны по структуре; новая логика ляжет куда попало | Каталог `domain/` — только чистые функции и типы, без Discord и базы |
| «Административная роль» = любой из 8 битов | Модераторы голоса, менеджеры веток и т. п. не видны; нет градаций | Каталог прав с уровнями → `roles::Tier`; staff = обычная роль уровня ≥ «Модерация» |
| 14 русских названий прав, остальные — английские из serenity | Сообщения вида «Manage Webhooks» | Полный каталог с названиями клиента Discord; неизвестные биты — «бит N» |
| Нет модели прав сервера | Главная задача бота не решалась | `domain::policy` + `/perms` |
| Интерфейс — подкоманды и формы | «Колхозность»: ни меню, ни страниц, ни подтверждений | `framework::view`: `Page`, `role_select`, `confirm_row`, `panel`; навигация между панелями |
| serenity 0.12 обрезает биты > 50 при чтении (`from_bits_truncate`) | Бот не видит «Закреплять сообщения» и «Обходить медленный режим»; при правке роли эти биты стёр бы | Константа `OBSERVABLE`: сравнение только по наблюдаемым битам; документированное ограничение; план перехода на serenity ≥ 0.13 |
| Нет Components V2 в serenity 0.12 | Контейнеры, секции, медиагалереи недоступны | Панели на embed + action rows (лимит 5 рядов); абстракция панели позволит сменить рендер без переписывания команд |

### 1.3. Ограничения платформы, учтённые в проектировании

* Ответ на взаимодействие — 3 секунды, токен живёт 15 минут. Долгие операции: `defer` →
  `edit_response` с прогрессом. Применение политики на сервере с сотнями каналов может не
  уложиться в 15 минут — операции идемпотентны, повторный запуск продолжает работу.
* Оверрайты канала можно менять только с «Управлять ролями» в этом канале, и только теми битами,
  которые есть у самого бота в канале (администратору доступно всё). План учитывает это
  поканально.
* Роль можно изменить, только если она строго ниже высшей роли бота; @everyone — всегда ниже.
* До 5 рядов компонентов, 5 кнопок в ряду, одно меню в ряду, 25 пунктов в меню, 100 символов в
  `custom_id`, 4096 символов в описании embed, 1024 — в поле.

## 2. Целевая архитектура

### 2.1. Слои и каталоги

```
src/
├── main.rs              точка входа: .env, журнал процесса, код выхода; BOT_NAME
├── app.rs               запуск: база → приложение → разработчики, интенты → команды → Gateway
├── config.rs            переменные окружения
├── state.rs             AppState: разработчики, интенты, настройки, журналы, ShardManager
├── error.rs             AppError (User | Discord | Storage), Fatal, Chain
│
├── commands.rs          реестр команд (ALL) и тесты ограничений Discord на определения
├── commands/            возможности бота — по модулю на команду, у сложных — подмодуль render
│   ├── ping.rs, say.rs (+ say/mentions.rs), embed.rs (+ embed/{color,draft}.rs)
│   ├── staff.rs (+ staff/render.rs)      администрация по уровням
│   ├── staff_edit.rs                      изменение состава администрации
│   ├── perms.rs (+ perms/render.rs)       политика прав: панели, аудит, план, применение
│   ├── access.rs, logs.rs, dev.rs
│
├── journal.rs, journal/ журналы сервера: доставка, обработчик событий, положение роли бота
│
├── framework.rs, framework/   инфраструктура взаимодействий; о командах не знает
│   ├── command.rs       SlashCommand, Cx, Registry
│   ├── handler.rs       маршрутизация, доступ к боту и право, отчёт об ошибках
│   ├── caller.rs        вызвавший участник и его права
│   ├── custom_id.rs     <команда>:<действие>[:<аргументы>…]
│   ├── input.rs         опции команд, поля форм, значения меню
│   ├── reply.rs         эфемерные ответы, сообщение об ошибке
│   └── view.rs          панели: страницы, подтверждение, меню ролей
│
├── domain.rs, domain/   ЧИСТАЯ ЛОГИКА — без Discord и базы, покрыта тестами
│   ├── permissions.rs   каталог прав: биты, названия, разделы, типы каналов, уровни
│   ├── roles.rs         классификация ролей: Tier × Origin
│   ├── hierarchy.rs     порядок ролей, план изменения администрации, положение бота
│   ├── access.rs        доступ к боту: режимы и правила
│   ├── policy.rs        политика прав: модель, разбор, план, моделирование, проверка
│   └── text.rs          укладывание текста в лимиты
│
├── settings.rs          настройки в памяти поверх базы
└── storage.rs           SQLite: миграции, чтение и запись
migrations/              0001_settings.sql, 0002_policy.sql
```

### 2.2. Принципы

1. **Зависимости сверху вниз:** `app` → `commands`/`journal` → `framework` → `domain` →
   `settings` → `storage`. `domain` не импортирует ничего выше себя; `framework` не знает команд.
2. **Решение — чистая функция, команда — адаптер.** Команда собирает снимок из Discord, вызывает
   функцию `domain`, исполняет результат и журналирует. Всё, что можно проверить без Discord,
   проверяется тестом.
3. **Из Discord — всё, что в нём есть.** Роли, права, оверрайты, владелец читаются в момент
   обращения. В базе — только решения администрации, которых в Discord нет: режимы доступа,
   каналы журналов, назначение ролей политики и классов каналов.
4. **Один путь изменения настроек** и **одна точка проверки доступа** (`Handler::cx`).
5. **Каждое действие от имени бота** — в журнал процесса (`target: audit`), системный журнал
   сервера и причину журнала аудита Discord.
6. **Панель = чистый рендер + состояние в `custom_id`.** Функции `render` возвращают
   `(CreateEmbed, Vec<CreateActionRow>)` и тестируются сериализацией в JSON.

### 3.1. Вычисление прав участника в канале

Алгоритм Discord, реализованный в `policy::effective` и используемый для проверки планов:

```
base      = perms(@everyone) ∪ ⋃ perms(role) по ролям участника
            (владелец или ADMINISTRATOR ⇒ все права, оверрайты не действуют)
step 1    = (base − deny(@everyone, c)) ∪ allow(@everyone, c)
step 2    = (step 1 − ⋃ deny(role, c)) ∪ ⋃ allow(role, c)      — по ролям участника
step 3    = (step 2 − deny(member, c)) ∪ allow(member, c)
неявно    : без VIEW_CHANNEL — ни одного права канала;
            без SEND_MESSAGES — ни MENTION_EVERYONE, ни TTS, ни ATTACH_FILES, ни EMBED_LINKS
тайм-аут  : остаются только VIEW_CHANNEL и READ_MESSAGE_HISTORY
```

Ключевое следствие шага 2: **разрешение любой роли перебивает запрет любой другой роли** в том же
канале. Именно поэтому мут-роли работают только в нейтральных каналах (§5).

## 4. Классификация ролей

Роль описывается двумя независимыми признаками (`domain/roles.rs`):

| `Tier` (по высшему уровню права) | Что входит |
|---|---|
| Администратор | `ADMINISTRATOR` |
| Управление | управлять сервером, ролями, каналами, вебхуками, выражениями; журнал аудита |
| Модерация | кик, бан, тайм-аут, сообщения, никнеймы, ветки, закрепление, микрофон/звук/перемещение, мероприятия |
| Доверенные | @everyone/@here, обход медленного режима, приоритетный режим, создание мероприятий и выражений, аналитика |
| Участники | только обычные права |
| Без прав | ни одного бита: цвет, разделитель, метка |

| `Origin` | Признак в данных Discord | Можно выдать вручную |
|---|---|---|
| Обычная | — | да |
| @everyone | `id == guild_id` | нет |
| Интеграция | `managed`, `tags.bot_id`, `tags.integration_id` | нет |
| Бусты | `tags.premium_subscriber` | нет |
| Подписка | `tags.subscription_listing_id` | нет |
| Связанная | `tags.guild_connections` | нет |

**Администрация** = обычная роль уровня ≥ «Модерация». Это определение используют `/staff`
(группы по уровням), `/staff-edit` (какие роли можно выдавать), `hierarchy::Standing`
(какими ролями может управлять бот) и политика (кому доверять оверрайты в каналах).

## 5. Политика прав сервера

### 5.1. Аксиомы модели

1. **@everyone не даёт ничего.** Участник без ролей не видит ни одного канала.
2. **Неверифицированный** не даёт ничего на уровне сервера; каналы верификации открыты ему
   оверрайтом (видеть, читать историю, нажимать кнопки). После верификации роль снимается и
   выдаётся роль участника.
3. **Участник** несёт базовые права на уровне роли (`MEMBER_BASELINE`: просмотр, сообщения,
   реакции, файлы, ссылки, голос, видео, опросы, команды приложений — без @everyone, TTS,
   приватных веток и приоритетного режима). В обычных каналах оверрайтов для него нет —
   **каналы нейтральны**.
4. **Роли-ограничения** (чат-мут, войс-мут) не дают ничего на уровне роли и в каждом канале несут
   запрет (`CHAT_MUTE`, `VOICE_MUTE`). Чат-мут не запрещает команды приложений — наказанный
   должен иметь возможность обратиться к боту.
5. **Закрытый канал** — запрет просмотра для @everyone и разрешение *только* ворот (`GATE` =
   просмотр + подключение) ролям из списка доступа. Остальное роль получает на уровне сервера.
6. **Канал только для чтения** — запрет записи (`WRITE`) для @everyone и разрешение записи
   авторам.
7. **Персональные оверрайты участников** бот не трогает (тикеты, личные комнаты).

### 5.2. Классы каналов и целевые оверрайты

| Класс | @everyone | Роли списка / авторы | Участник | Неверифицированный | Муты |
|---|---|---|---|---|---|
| Открытый | deny: сохранённые ограничения канала | — | нет оверрайта | нет | deny `CHAT_MUTE`; в голосе и категориях — deny `VOICE_MUTE` |
| Закрытый | deny `VIEW_CHANNEL` + сохранённые | allow `GATE` (+ то, что снимает запрет @everyone) | нет (если не в списке) | нет (если не в списке) | то же |
| Только чтение | deny `WRITE` + сохранённые | allow `WRITE` | нет | нет | то же |
| Верификация | deny `VIEW_CHANNEL` + сохранённые | кто видит сейчас, кроме участника | нет | allow `UNVERIFIED_GATE` + уже разрешённое | то же |
| Не трогать | — | — | — | — | — |

Класс канала либо задан явно (`/perms channel`), либо **выводится** из текущих оверрайтов:
запрет просмотра у @everyone ⇒ закрытый (список — роли с разрешением просмотра; если среди них
неверифицированный и нет участника ⇒ верификация); запрет записи ⇒ только чтение; иначе открытый.
Запреты роли участника учитываются как запреты @everyone и переносятся туда — так они действуют и
на всех остальных.

### 5.3. Инвариант безопасности мутов

> Для каждого канала `c` и каждой неадминистративной роли `r`:
> `allow(c, r) ∩ MUTE_BITS ⊆ deny(c, @everyone)`.

Разрешение в канале может лишь **снимать ограничение, наложенное на всех** (авторы в канале
только для чтения), но не выдавать то, что роль должна получать на уровне сервера.

**Теорема.** Если инвариант выполнен, участник `m` с ролью чат-мута, без персонального оверрайта
и вне администрации, не имеет битов `CHAT_MUTE ∩ applicable(c)` ни в одном канале `c`.

*Доказательство.* По §3.1: `step 1 ⊆ base − deny(@everyone)`; на шаге 2 чат-мут добавляет в
объединённый запрет `CHAT_MUTE ∩ applicable`, а объединённое разрешение ролей `m` пересекается с
`MUTE_BITS` только внутри `deny(@everyone)`, биты которого уже сняты на шаге 1 и могут вернуться
лишь разрешением — а в закрытом канале разрешения ролей списка ограничены воротами, не
пересекающимися с `MUTE_BITS`; для авторов канала только для чтения разрешение записи и есть
`deny(@everyone)`, и такой автор пишет вопреки муту — это единственное допущение, и план
отмечает авторов вне администрации. Шаг 3 отсутствует по условию. ∎

Планировщик **восстанавливает** инвариант: разрешения неадминистративных ролей, пересекающие
`MUTE_BITS` вне запрета @everyone, снимаются с предупреждением. Администрации доверяют целиком —
её оверрайты не меняются. Инвариант проверяется тестом на смоделированном состоянии после плана.

### 5.4. Планировщик

`policy::plan(snapshot, policy) → Plan { ops, findings, classes }`:

1. **Предпосылки** (блокируют план): у бота есть «Управлять ролями»; роли политики существуют,
   обычные и различны; роли политики ниже роли бота (кроме @everyone).
2. **Роли сервера:** @everyone → `everyone_permissions` (∅), участник → `member_permissions`,
   неверифицированный и муты → ∅. Операция только при различии в наблюдаемых битах.
3. **Обзор:** администрация по уровням; интеграции с опасными правами (не меняются).
4. **Каналы** (категории, затем каналы по категории и позиции; ветки пропускаются): класс →
   целевые оверрайты (§5.2) → операции `SetOverwrite` / `DeleteOverwrite` только при различии
   и только теми битами, которые бот может выставить в канале. Каналы, где бот не видит или не
   управляет правами, пропускаются с предупреждением.

Свойства, проверенные тестами:

* **Минимальность** — только различия в наблюдаемых битах.
* **Идемпотентность** — `plan(simulate(s, plan(s).ops)) = ∅`, классы устойчивы.
* **Сохранение намерений** — доступ людей не меняется, кроме того, что требует модель; каждое
  такое изменение — отдельное замечание (`Finding`) с уровнем ℹ️ / ⚠️ / ⛔.
* **Проверка модели** (`policy::verify`) на состоянии после плана: без ролей не виден ни один
  канал; участник видит открытые каналы; неверифицированный видит только верификацию; чат-мут
  запрещает писать везде, где участник может; войс-мут позволяет подключаться, но не говорить.

### 5.5. Применение

`/perms sync` показывает план и кнопку «Применить (N)», несущую **отпечаток плана** (FNV-1a по
операциям). При нажатии план строится заново; если сервер изменился — показывается новый план,
а не применяется старый. Операции идут по порядку (роли → категории → каналы) с причиной для
журнала аудита Discord; остановка на первой ошибке с отчётом, что выполнено. Прогресс — каждые
10 операций. Итог — в системный журнал сервера.

### 5.6. Ограничения

* Биты 51–52 не наблюдаемы (serenity 0.12): сохранённые запреты @everyone по ним теряются,
  целевые права ролей политики задаются полностью и уходят верно.
* Оверрайты «неизвестного вида» (не роль и не участник) не трогаются.
* Применение привязано к токену взаимодействия (15 минут): для очень больших серверов — несколько
  запусков; выполненное не повторяется.

## 6. Интерактивный слой («приложения»)

Панель — эфемерное сообщение с embed и до 5 рядов компонентов; каждый шаг заменяет его целиком
(`UpdateMessage`) или откладывает (`Acknowledge` → `edit_response`), если нужен запрос к
Discord. Состояние — в `custom_id`: `<команда>:<действие>[:<аргументы>…]`.

`framework::view` даёт строительные блоки: `Page` (страницы с кнопками ◀ n/N ▶), `role_select`
(меню ролей с текущим выбором), `confirm_row` (подтверждение с аргументами), `panel`.
`framework::input::selected_roles` читает выбор. Рендер панели — чистая функция в
`commands/<команда>/render.rs`, проверяемая сериализацией в JSON (лимиты, `custom_id`, ряды).

Переход на **Components V2** (контейнеры, секции, медиа, до 40 компонентов) требует serenity с
их поддержкой (ветка `next` / 0.13). Поскольку команды работают с `(CreateEmbed,
Vec<CreateActionRow>)` через функции `render`, замена рендера локализована.

## 7. Планируемые подсистемы — проектные решения

### 7.1. Верификация и модерация поверх политики

Политика делает эти команды тривиальными и безопасными:

* **Верификация:** в канале класса «верификация» бот публикует панель с кнопкой; нажатие →
  снять `unverified`, выдать `member` (проверка: роли политики заданы и ниже роли бота), запись
  в системный журнал. Для варианта «через команду» — `/verify @user`.
* **`/mute chat|voice @user [duration] [reason]`:** выдать роль мута из политики (все запреты уже
  стоят в каналах, инвариант гарантирует действие), записать дело; снятие по таймеру — таблица
  `moderation_cases(guild_id, case_id, kind, target, actor, reason, until, active)` и фоновая
  задача `tokio::time` с восстановлением при запуске; `/unmute`, `/cases @user`.
* **`/warn`, `/kick`, `/ban`** — те же дела, с проверкой иерархии (`hierarchy::plan`-подобная
  функция для действий над участником: цель ниже автора и ниже бота; авторское право есть).

### 7.2. Голосовые комнаты

* **Данные:** `voice_hubs(guild_id, hub_channel_id, category_id, panel_channel_id, name_template,
  default_limit)`, `voice_rooms(guild_id, channel_id, owner_id, hub_channel_id, panel_message_id,
  locked, hidden)`. Комнаты восстанавливаются при запуске: пустые удаляются, живые — переучитываются.
* **Жизненный цикл:** `voice_state_update`: вход в хаб → создать канал в категории хаба
  (имя по шаблону, лимит), персональный оверрайт владельца (`MANAGE_CHANNELS`, `MOVE_MEMBERS`,
  `MUTE_MEMBERS`, `DEAFEN_MEMBERS`, `PRIORITY_SPEAKER`), переместить владельца; выход
  последнего → удалить канал. Категория хаба назначается классом **«не трогать»** в политике
  — но муты продолжают действовать: канал наследует запреты категории, которые ставит план.
* **Панель** (одно сообщение в канале панели, кнопки с кастомными эмодзи сервера, 2 ряда по
  4–5): 🔒 закрыть / 🔓 открыть (deny/allow `CONNECT` для @everyone... точнее — для роли
  участника политики через оверрайт класса «закрытый»), 👁 скрыть / показать, 👥 лимит
  (форма), ✏️ переименовать (форма), 👢 выгнать (меню участников), 👑 передать владение
  (меню), 🎙 заглушить гостя. Действие проверяет, что нажавший — владелец комнаты, в которой он
  сейчас находится (`VoiceState`), и что бот имеет права в канале.
* **Безопасность:** все оверрайты комнаты — персональные или для роли участника; инвариант
  мутов не нарушается, так как муты стоят запретом на категории.

### 7.3. Музыка

* **Стек:** `songbird 0.6` (совместим с serenity ^0.12; `davey` для обязательного шифрования
  DAVE), источник `yt-dlp` (внешний бинарь) и прямые ссылки; при желании — Lavalink вместо
  встроенного драйвера (меньше нагрузки на процесс бота).
* **Структура:** отдельный модуль `music/` с состоянием на сервер (очередь, текущий трек,
  громкость, канал панели), команды `/play`, `/skip`, `/stop`, `/queue`, `/volume` и панель
  плеера с кнопками (⏯ ⏭ ⏹ 🔁 🔀). Права: подключение в канал, где находится автор; «DJ» —
  роль уровня ≥ «Доверенные» или заданная в настройках.
* **Сборка:** feature `music` в `Cargo.toml`, чтобы основная сборка не тянула аудиостек.

### 7.4. Журнал участников

Вход, выход, смена ролей и ников — по образцу журналов сообщений и голоса (`journal/members.rs`),
требует Server Members Intent; изменения ролей политики (мут, верификация) помечаются особо.

## 10. Что проверяют тесты

* **Каталог:** полнота битов 0–52 (без 47), уникальность, разбиение по уровням, применимость к
  типам каналов, неявные запреты, русские названия и «бит N».
* **Роли:** уровень по правам, происхождение по тегам, определение администрации.
* **Иерархия:** порядок Discord, высоты, план изменения администрации, положение бота.
* **Политика:** роли → модель; вывод классов; нейтральность открытых каналов и запреты мутов;
  ворота закрытых; верификация; только чтение; **идемпотентность**; **инвариант мутов** до и
  после; **эффективные права** участника, неверифицированного, замученных, модератора;
  блокировки; ограничения бота поканально; явные классы; перенос запретов участника; отпечаток.
* **Панели:** страницы и `custom_id`, лимиты описаний и полей, наличие подтверждения только когда
  план применим, справочник прав.
* **Хранение:** round-trip политики с каналами и ролями, каскадное удаление, биты прав.
* **Определения команд:** ограничения Discord на имена, описания, опции и подкоманды.
