# Axiom — техническая документация

Discord-бот на **Rust 2024**, **Serenity 0.12** и **Tokio**. Команды — только через
взаимодействия (слэш-команды, кнопки, формы); события сервера бот читает для журналов. Настройки
серверов хранятся в **SQLite** (sqlx), всё остальное — роли, права, владелец — читается из
Discord в момент обращения.

---

## 1. Запуск

```sh
cp .env.example .env   # заполнить DISCORD_TOKEN
cargo run --release
```

| Переменная       | Обязательна | Назначение                                                    |
|------------------|-------------|---------------------------------------------------------------|
| `DISCORD_TOKEN`  | да          | Токен бота                                                    |
| `BOT_DEVELOPERS` | нет         | ID разработчиков через запятую                                |
| `DATABASE_PATH`  | нет         | Файл базы настроек, по умолчанию `axiom.db`                   |
| `RUST_LOG`       | нет         | Фильтр журнала, по умолчанию `info,axiom=debug`               |
| `HTTPS_PROXY`    | нет         | Прокси для REST API: `http://`, `socks5://`, `socks5h://`     |

**Имя бота** задаётся в Developer Portal → Bot → Username: Discord ограничивает частоту его
смены, поэтому бот не меняет его сам, а при подключении предупреждает в журнале, если имя
аккаунта отличается от «Axiom».

**Developer Portal → Bot → Privileged Gateway Intents:**

| Интент              | Без него                                                                  |
|---------------------|---------------------------------------------------------------------------|
| Server Members      | `/staff` не получит список участников; изменения ролей самого бота станут заметны с задержкой |
| Message Content     | журнал сообщений записывает удаления без текста и не видит изменений       |

Бот запрашивает привилегированный интент, только если он включён в Developer Portal (флаги
приложения читаются при запуске), — поэтому выключенный интент не мешает запуску, а лишь
отключает часть возможностей с предупреждением в журнале.

**Права бота на сервере:** просматривать каналы, отправлять сообщения, встраивать ссылки,
прикреплять файлы (журнал сообщений); «Управлять ролями» — для `/staff-edit` и `/perms`
(изменение ролей и оверрайтов каналов; оверрайт можно выставить только теми правами, которые есть
у бота в этом канале); для уведомляющих упоминаний ролей в `/say` — «Упоминание @everyone, @here
и всех ролей». **Роль бота** должна стоять выше ролей, которыми он будет управлять:
административных (`/staff-edit roles` покажет, где она сейчас) и ролей политики (`/perms sync`
сообщит, если роль бота ниже).

**Порядок запуска.** Бот открывает базу и применяет миграции (они встроены в бинарник),
получает данные приложения (заодно проверяя токен), определяет разработчиков и интенты,
регистрирует слэш-команды и только потом подключается к Gateway. Любая ошибка на этих шагах
останавливает процесс с понятным сообщением и всей цепочкой причин в журнале.

**Остановка** — `Ctrl+C`, а на Linux также `SIGTERM` (systemd, Docker): бот корректно закрывает
соединение с Gateway.

**Прокси.** REST-запросы учитывают `HTTP_PROXY`/`HTTPS_PROXY`/`ALL_PROXY`. Gateway (WebSocket)
всегда подключается напрямую: serenity 0.12 не поддерживает для него прокси.

## 2. Модель доступа

В коде нет ни одного ID сервера, роли или пользователя. Перед **каждым** шагом взаимодействия
(команда, кнопка, форма) `framework::Handler` проверяет два независимых условия: доступ к боту и
право Discord, которое требует команда. Поэтому отзыв доступа или смена режима действуют и на
уже открытые формы.

### Доступ к боту (`access`)

Проверки идут по порядку, первый отказ — итог:

| # | Уровень | Правило |
|---|---------|---------|
| 1 | Разработчики бота | проходят всегда — не запрут сами себя ни режимом, ни ошибкой в правилах |
| 2 | Команды разработчиков | только разработчикам |
| 3 | Режим приложения | `public` или `dev-only` (обслуживание: только разработчики) |
| 4 | Глобальная блокировка | пользователь заблокирован разработчиками — на всех серверах |
| 5 | Управляющие ботом на сервере | «Администратор», «Управлять сервером» или владелец — проходят: кто может изменить правила, тот им не подчиняется, поэтому администрация не может запереть сама себя |
| 6 | Режим сервера `locked` | только управляющие (п. 5) |
| 7 | Правила сервера | правило пользователя важнее правил его ролей (как оверрайты каналов); среди ролей запрет важнее разрешения |
| 8 | Режим сервера по умолчанию | `open` — разрешено, `restricted` — только по правилам |

Логика — чистая функция `access::check`, таблица истинности покрыта тестами.

### Права на сервере — только из Discord

* Каждая команда объявляет требуемое право (`SlashCommand::permission`). Из него строится
  `default_member_permissions` — Discord не показывает команду тем, у кого его нет.
* Права берутся из Discord в момент запроса. В канале взаимодействия Discord присылает их уже
  вычисленными (роли, оверрайты, владение сервером, тайм-аут). Для другого канала бот считает их
  по кэшу и сам применяет тайм-аут.
* Сервер может настроить доступ к команде в «Настройки сервера → Интеграции», но выдать её тому,
  у кого нет требуемого права, не получится: бот откажет.

### Разработчики бота — уровень приложения

Разработчики не связаны с конкретным сервером: `BOT_DEVELOPERS` ∪ участники команды приложения
в Developer Portal со статусом Accepted (или владелец, если команды нет). Статус разработчика
открывает `/dev` и проходит доступ к боту (п. 1), но **не даёт прав на сервере**: например,
`/access` требует «Управлять сервером» и от разработчика. Команды разработчиков Discord
показывает только администраторам серверов (`default_member_permissions = 0`), а выполняет бот
только для разработчиков.

### Защита от «доверенного посредника»

У бота широкие права, поэтому он не делает за автора то, что автор не может сделать сам:

* `/say` и `/embed` публикуют только туда, где у автора есть «Просматривать каналы» и
  «Отправлять сообщения» (в ветке — «Отправлять сообщения в ветках»), для embed ещё
  «Встраивать ссылки». Права проверяются и до открытия формы, и непосредственно перед отправкой.
* В `/say` упоминания по умолчанию никого не уведомляют; с `mentions: true` — только те, которые
  автор мог бы вызвать сам.
* `/staff-edit` выдаёт и снимает только роли ниже высшей роли автора, только участникам ниже
  автора и только роли, все права которых есть у автора (см. §4).
* Журналы сообщений и голоса может включить только тот, кто видит все каналы, которые они
  охватят (см. §5).

Каждое действие от имени бота пишется в журнал процесса с target `audit` и в системный журнал
сервера: в Discord автором будет бот, а реальный автор виден только там.

## 3. Команды

| Команда | Доступ | Описание |
|---|---|---|
| `/ping` | все | Задержка Gateway и REST API, время работы, версия |
| `/say [text] [channel] [mentions]` | «Управлять сервером» | Сообщение от имени бота. Без `text` открывается форма для многострочного текста |
| `/embed [channel] [color] [timestamp]` | «Управлять сервером» | Форма → предпросмотр → «Опубликовать»/«Отмена» |
| `/staff [public]` | все | Владелец сервера, разработчики бота и администрация по уровням |
| `/staff-edit add\|remove\|set\|roles` | «Управлять ролями» | Изменить состав администрации; положение роли бота |
| `/perms setup\|channel\|audit\|sync\|catalog` | «Управлять сервером» и «Управлять ролями» | Политика прав: роли, назначение каналов, аудит, план и применение, справочник прав |
| `/access status\|mode\|allow\|deny\|reset` | «Управлять сервером» | Доступ к боту на сервере |
| `/logs status\|set\|disable` | «Управлять сервером» | Каналы журналов сервера |
| `/dev status\|mode\|block\|unblock` | разработчики | Режим бота и глобальные блокировки |

Все команды работают только на серверах.

### `/embed`

* `color` — HEX (`#5865F2`, `0x5865F2`, `5865F2`, `#F00`) или название: `blurple`, `green`,
  `yellow`, `fuchsia`/`pink`, `red`, `white`, `black`, `dark` (и русские названия).
* Форма: заголовок, текст (Markdown), баннер, миниатюра, подпись. Проверяются лимиты Discord:
  заголовок 256, текст 4096, подпись 2048, всего 6000 символов; ссылки — только `http(s)://`.

### `/staff`

* «Административная» роль — обычная роль (не @everyone, не интеграция, не бусты и не подписка)
  уровня не ниже «Модерация» по каталогу прав (`ARCHITECTURE.md`, §3–4): администратор;
  управление сервером, ролями, каналами, вебхуками, выражениями, журнал аудита; кик, бан,
  тайм-аут, сообщения, никнеймы, ветки, закрепление, микрофон, звук, перемещение, мероприятия.
* Группы — по уровням (👑 администраторы, 🛡️ управление, ⚖️ модерация), внутри уровня — по
  старшинству; участник показывается один раз — под своей высшей административной ролью. Текст
  никогда не превышает лимит embed.

### `/perms`

Политика прав сервера — модель «@everyone не даёт ничего, участник получает базовые права на
уровне роли, каналы нейтральны, роли мутов запрещают в каждом канале». Модель, инварианты и
алгоритм — `ARCHITECTURE.md`, §5.

| Подкоманда | Действие |
|---|---|
| `setup` | Панель с меню ролей: участник (обязательна), неверифицированный, чат-мут, войс-мут. Выбор сохраняется сразу |
| `channel channel class` | Назначить каналу или категории класс: 🌐 открытый, 🔒 закрытый (меню ролей доступа), 📢 только чтение (меню авторов), 🛂 верификация, ⏸️ не трогать, 🧭 по оверрайтам (сбросить) |
| `audit` | Замечания и класс каждого канала, ничего не меняя |
| `sync` | План изменений с проверкой модели после применения и кнопкой «Применить» |
| `catalog` | Справочник всех прав Discord: название, ключ, уровень, где действует |

* Каналы без явного назначения классифицируются по текущим оверрайтам: запрет просмотра у
  @everyone — закрытый (верификация, если доступ есть у неверифицированного и нет у участника),
  запрет записи — только чтение, иначе открытый.
* План меняет только то, что требует модель; каждое изменение доступа людей — отдельное
  замечание. Разрешения неадминистративных ролей, которые перебивали бы муты, снимаются с
  предупреждением. Персональные оверрайты участников не трогаются.
* Кнопка «Применить» несёт отпечаток плана: если сервер изменился после предпросмотра, бот
  покажет новый план вместо применения старого. Операции идемпотентны — при ошибке повторный
  `sync` продолжит с места остановки.
* Ограничение serenity 0.12: права «Закреплять сообщения» и «Обходить медленный режим» бот
  выдавать может, а видеть у ролей — нет.

### `/access`

* `mode` — `open` (все, кроме закрытых правилами), `restricted` (только с выданным доступом),
  `locked` (только администрация; правила сохраняются, но не действуют).
* `allow`/`deny` — правило для пользователя или роли (не больше одного на субъекта, всего до
  100); `reset` — снять правило. Для @everyone используется режим, а не правило.
* Бот предупреждает, если правило ни на что не повлияет: у субъекта есть «Управлять сервером»
  или режим `locked`.

### `/dev`

* `mode` — `public` или `dev-only` (обслуживание). Режим хранится в базе и переживает перезапуск.
* `block`/`unblock` — глобальная блокировка пользователя; разработчика заблокировать нельзя.

## 4. Состав администрации (`/staff-edit`)

| Подкоманда | Действие |
|---|---|
| `add member role [reason]` | выдать административную роль |
| `remove member [role] [reason]` | снять роль; без `role` — все административные роли участника |
| `set member role [reason]` | назначить на должность: выдать роль и снять остальные административные |
| `roles` | административные роли с отметками, кто может ими управлять, и положение роли бота |

Изменение выполняется, только если **все** правила выполнены (`hierarchy::plan`, покрыто
тестами); при любом нарушении не меняется ничего:

1. У бота есть «Управлять ролями», и каждая затронутая роль строго ниже высшей роли бота
   (иначе Discord откажет — бот объясняет, что роль бота нужно поднять).
2. У автора есть «Управлять ролями», и каждая затронутая роль строго ниже его высшей роли.
3. Участник строго ниже автора; исключение — снять роль с самого себя (сложить полномочия).
4. Выдать можно только роль, все права которой есть у автора.
5. Затрагиваются только административные роли — не @everyone и не роли интеграций; боты в
   администрацию не входят.

Владелец сервера не ограничен пп. 2–4. Порядок ролей — как в Discord: выше позиция — старше,
при равных позициях старше роль с меньшим ID.

Сначала выдаётся новая роль, затем снимаются старые — участник не остаётся посередине без
должности. Причина и автор попадают в журнал аудита Discord и в системный журнал.

### Положение роли бота

Бот знает свою высшую роль, её место сверху и какими административными ролями может управлять
(`hierarchy::Standing`). После любых изменений ролей сервера (с паузой 3 с, чтобы перестановка
ролей дала одну проверку) он сравнивает это с прошлым состоянием и пишет в системный журнал,
если возможности изменились: роль бота опустили ниже административной роли, отобрали
«Управлять ролями» и т. п.

## 5. Журналы сервера (`/logs`)

| Журнал | Что записывается |
|---|---|
| Сообщения | изменение (было → стало), удаление (автор, текст, вложения), массовое удаление (расшифровка файлом) |
| Голосовые каналы | вход, выход, переход между каналами |
| Системный | изменения доступа и журналов, состава администрации, политики прав и её применение, публикации `/say` и `/embed`, положение роли бота, неполадки журналов |

* **Выбор канала** проверяется сразу: бот должен иметь в нём «Просматривать каналы»,
  «Отправлять сообщения», «Встраивать ссылки» (для журнала сообщений — и «Прикреплять файлы»);
  автор должен его видеть.
* **Журнал сообщений и голоса** может включить только тот, кто сам видит все каналы, которые
  они охватят: иначе бот открыл бы ему содержимое закрытых каналов.
* **Журнал сообщений** ведётся только в канале, закрытом для @everyone. Если канал позже
  станет виден всем, журнал приостанавливается (с предупреждением в системном журнале), пока
  канал не закроют.
* **Память сообщений.** Discord сообщает об удалении только ID, поэтому бот помнит последние
  200 сообщений каждого канала — только на серверах с включённым журналом сообщений и только
  автора, текст и имена вложений. Память не переживает перезапуск; о более старых сообщениях
  известны только ID и время отправки. Выключение журнала стирает память сервера.
* Сообщения ботов, вебхуков и сами каналы журналов в журнал не попадают. Служебные обновления
  (превью ссылок) — не изменения.
* Записи отправляются без уведомлений: упоминания только отображаются.
* Если бот не может писать в журнал, он сообщает об этом в системный журнал (не чаще раза в час);
  если канал журнала удалён, журнал выключается.

## 6. Архитектура

Зависимости направлены сверху вниз:

```
src/
├── main.rs              точка входа: .env, журнал, код выхода; BOT_NAME
├── app.rs               запуск: база → приложение → разработчики, интенты → команды → Gateway
├── config.rs            переменные окружения (токен, BOT_DEVELOPERS, DATABASE_PATH)
├── state.rs             AppState: разработчики, интенты, настройки, журналы, ShardManager
├── error.rs             AppError (User | Discord | Storage), Fatal, Chain
│
├── commands.rs          реестр команд (ALL) и тест ограничений Discord на определения
├── commands/            возможности бота — по модулю на команду; панели — в подмодуле render
│   ├── ping.rs, say.rs (+ say/mentions.rs), embed.rs (+ embed/{color,draft}.rs)
│   ├── staff.rs (+ staff/render.rs)   администрация по уровням
│   ├── staff_edit.rs    /staff-edit: ввод, выполнение плана, журналы
│   ├── perms.rs (+ perms/render.rs)   /perms: панели, аудит, план, применение, справочник
│   ├── access.rs        /access
│   ├── logs.rs          /logs: проверки канала
│   └── dev.rs           /dev
├── journal.rs           журналы сервера: доставка, обработчик событий Gateway, положение роли
├── journal/
│   ├── messages.rs      память сообщений, записи об изменении и удалении (тесты)
│   ├── voice.rs         переходы между голосовыми каналами (тесты)
│   └── system.rs        записи системного журнала
│
├── domain.rs            чистая логика — без Discord и базы, покрыта тестами
├── domain/
│   ├── permissions.rs   каталог прав Discord: биты, названия, разделы, типы каналов, уровни
│   ├── roles.rs         классификация ролей: уровень полномочий × происхождение
│   ├── hierarchy.rs     иерархия ролей, план изменения администрации, положение бота
│   ├── access.rs        доступ к боту: режимы, правила, решение
│   ├── policy.rs        политика прав: модель, вывод классов, план, моделирование, проверка
│   └── text.rs          укладывание текста в лимиты
├── settings.rs          настройки в памяти поверх базы; изменение — копия → база → память
├── storage.rs           SQLite: открытие, миграции, чтение и запись настроек (тесты)
│
├── framework.rs         инфраструктура взаимодействий; о конкретных командах не знает
└── framework/
    ├── command.rs       SlashCommand (право, команды разработчиков), Cx, Registry
    ├── handler.rs       маршрутизация, доступ к боту и право, отчёт об ошибках
    ├── caller.rs        вызвавший участник и его права
    ├── custom_id.rs     формат custom_id кнопок, меню и форм
    ├── input.rs         опции команд (включая подкоманды), поля форм, значения меню
    ├── reply.rs         ответы: эфемерные сообщения и embed, сообщение об ошибке
    └── view.rs          панели: страницы, подтверждение, меню ролей
migrations/              схема базы; встраивается в бинарник (`sqlx::migrate!`, build.rs)
```

Принципы (подробно — `ARCHITECTURE.md`):

* **Зависимости сверху вниз:** `app` → `commands`/`journal` → `framework` → `domain` →
  `settings` → `storage`. `framework` не зависит от `commands` и `journal`: команды передаются
  через `Registry`, события журналов обрабатывает отдельный `journal::Watcher`.
* **Чистая логика отделена от ввода-вывода.** Всё, что можно решить без Discord, — функции в
  `domain` (и в подмодулях `render`), покрытые тестами; команды и обработчики только собирают
  данные, выполняют решение и журналируют.
* **Из Discord — всё, что в нём есть.** Роли, права, оверрайты, владелец читаются в момент
  обращения; в базе — только решения администрации и разработчиков, которых в Discord нет.
* **Панель = чистый рендер + состояние в `custom_id`.** Функции `render` возвращают embed и
  ряды компонентов; тесты проверяют их сериализацию (лимиты, `custom_id`, число рядов).
* **Стиль модулей** — `foo.rs` рядом с каталогом `foo/`, без `mod.rs`
  (`clippy::mod_module_files`).

### Хранение настроек

* Таблицы: `global_settings` (режим приложения), `blocked_users`, `guild_settings` (режим
  сервера, каналы журналов), `access_rules`, `guild_policy` (роли политики, права @everyone и
  участника), `channel_policy` и `channel_policy_roles` (явное назначение каналов). Сервер с
  настройками по умолчанию в базе не хранится; удаление строки сервера каскадно очищает всё
  его. ID Discord и наборы прав хранятся как INTEGER с тем же битовым представлением.
* Настройки читаются из памяти (они нужны на каждом взаимодействии и событии), а изменяются по
  одному пути: копия → изменение → транзакция в базе → публикация в памяти. Изменения идут
  строго по одному, поэтому не затирают друг друга; неудачная запись ничего не меняет.
* Удаление бота с сервера стирает только память сообщений; настройки остаются на случай
  повторного приглашения.

### Поток взаимодействия

1. `Handler` находит команду-владельца: слэш-команду по имени, кнопку или форму — по первому
   сегменту `custom_id`. Неизвестное взаимодействие получает ответ «Это действие устарело».
2. `Handler` строит `Caller`, проверяет доступ к боту (`access::check`) и право команды.
3. Обработчик получает `Cx` — serenity-контекст, состояние и проверенного вызывающего.
4. При ошибке `Handler` пишет её в журнал и показывает эфемерное сообщение: текст
  `AppError::User` как есть, для `Discord`/`Storage` — понятное описание.

### Состояние между шагами

`custom_id` имеет вид `<команда>:<действие>[:<аргументы>…]`. Состояние диалога передаётся в нём
самом, поэтому открытые формы переживают перезапуск. Аргументы приходят от клиента, поэтому
каждый шаг проверяет их заново, как и доступ.

### Gateway

* Интенты: `GUILDS`, `GUILD_MESSAGES`, `GUILD_VOICE_STATES`, а `MESSAGE_CONTENT` и
  `GUILD_MEMBERS` — если включены в Developer Portal.
* Команды регистрируются глобально при запуске, до подключения к Gateway. Это полная
  перезапись: команды, удалённые из кода, исчезают из Discord.

### Как добавить команду

1. Создать `commands/<имя>.rs` с типом, реализующим `SlashCommand`: `name`, `description`,
   при необходимости `options`, `permission`, `developer_only`, обязательно `run`; для кнопок,
   меню и форм — `component`/`modal` (их `custom_id` строится через `CustomId::encode(NAME, …)`).
2. Панели собирать из `framework::view` (`Page`, `role_select`, `confirm_row`, `panel`), а их
   текст — в `commands/<имя>/render.rs` чистыми функциями с тестами.
3. Добавить модуль и тип в `commands.rs` (`mod <имя>;` и элемент массива `ALL`).

Регистрация, маршрутизация, доступ и право подключатся автоматически; `cargo test` проверит
определение команды (включая подкоманды) на соответствие ограничениям Discord.
