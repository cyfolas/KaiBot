# KaiBot — техническая документация

Discord-бот на **Rust 2024**, **Serenity 0.12** и **Tokio**. Работает только через взаимодействия
(слэш-команды, кнопки, формы) и не читает содержимое сообщений.

---

## 1. Запуск

```sh
cp .env.example .env   # заполнить DISCORD_TOKEN
cargo run --release
```

| Переменная       | Обязательна | Назначение                                                    |
|------------------|-------------|---------------------------------------------------------------|
| `DISCORD_TOKEN`  | да          | Токен бота                                                    |
| `BOT_DEVELOPERS` | нет         | ID разработчиков через запятую                                |
| `RUST_LOG`       | нет         | Фильтр журнала, по умолчанию `info,kaibot=debug`              |
| `HTTPS_PROXY`    | нет         | Прокси для REST API: `http://`, `socks5://`, `socks5h://`     |

**Developer Portal → Bot → Privileged Gateway Intents:** включите **Server Members Intent** — без
него `/staff` не сможет получить список участников. Остальные привилегированные интенты не нужны.

**Права бота на сервере:** просматривать каналы, отправлять сообщения, встраивать ссылки; для
уведомляющих упоминаний ролей в `/say` — «Упоминание @everyone, @here и всех ролей».

**Порядок запуска.** Бот получает данные приложения (заодно проверяя токен), определяет
разработчиков, регистрирует слэш-команды и только потом подключается к Gateway. Любая ошибка на
этих шагах останавливает процесс с понятным сообщением и всей цепочкой причин в журнале.

**Остановка** — `Ctrl+C`, а на Linux также `SIGTERM` (systemd, Docker): бот корректно закрывает
соединение с Gateway.

**Прокси.** REST-запросы учитывают `HTTP_PROXY`/`HTTPS_PROXY`/`ALL_PROXY`. Gateway (WebSocket)
всегда подключается напрямую: serenity 0.12 не поддерживает для него прокси.

## 2. Модель доступа

В коде нет ни одного ID сервера, роли или пользователя. Доступ складывается из двух
независимых уровней.

### Права на сервере — только из Discord

* Каждая команда объявляет требуемое право (`SlashCommand::permission`). Из него строится
  `default_member_permissions` — Discord не показывает команду тем, у кого его нет.
* То же право `framework::Handler` проверяет **централизованно, перед каждым шагом**: командой,
  кнопкой, формой. У кнопок и форм нет собственной защиты со стороны Discord, а проверка в одном
  месте исключает ситуацию, когда команда объявила право, но забыла его проверить.
* Права берутся из Discord в момент запроса. В канале взаимодействия Discord присылает их уже
  вычисленными (роли, оверрайты, владение сервером, тайм-аут). Для другого канала бот считает их
  по кэшу и сам применяет тайм-аут.
* Сервер может настроить доступ к команде в «Настройки сервера → Интеграции» (роли, участники,
  каналы), но выдать её тому, у кого нет требуемого права, не получится: бот откажет.

Поэтому иерархия ролей (⚝, Admin, Технопсих и т. д.) живёт только на сервере: переименование,
пересоздание или изменение прав роли действует сразу, без правок кода и перезапуска.

### Разработчики бота — уровень приложения

Разработчики не связаны с конкретным сервером: `BOT_DEVELOPERS` ∪ участники команды приложения
в Developer Portal со статусом Accepted (или владелец, если команды нет). Рекомендуется создать
команду (Developer Portal → Teams), добавить в неё всех разработчиков и передать ей приложение:
тогда список полностью определяется Developer Portal, а `BOT_DEVELOPERS` можно не заполнять.

Статус разработчика не даёт прав на сервере. Сейчас разработчики показываются в `/staff`;
команды только для разработчиков смогут проверять их через `AppState::developers`.

### Защита от «доверенного посредника»

У бота права администратора, поэтому он не должен делать за автора то, что автор не может
сделать сам:

* `/say` и `/embed` публикуют только туда, где у автора есть «Просматривать каналы» и
  «Отправлять сообщения» (в ветке — «Отправлять сообщения в ветках»), для embed ещё
  «Встраивать ссылки». Права проверяются и до открытия формы, и непосредственно перед отправкой.
* В `/say` упоминания по умолчанию никого не уведомляют. С `mentions: true`:
  * пользователей — уведомляет всегда;
  * роли — только упоминаемые (`mentionable`);
  * `@everyone`, `@here` и неупоминаемые роли — только если у автора есть право
    «Упоминание @everyone, @here и всех ролей» в целевом канале.

Каждая публикация от имени бота пишется в журнал с target `audit` (автор, канал, сообщение):
в Discord автором будет бот, а реальный автор виден только там.

## 3. Команды

| Команда | Доступ | Описание |
|---|---|---|
| `/ping` | все | Задержка Gateway и REST API, время работы, версия |
| `/say [text] [channel] [mentions]` | «Управлять сервером» | Сообщение от имени бота. Без `text` открывается форма для многострочного текста (до 2000 символов) |
| `/embed [channel] [color] [timestamp]` | «Управлять сервером» | Форма → предпросмотр → «Опубликовать»/«Отмена» |
| `/staff [public]` | все | Владелец сервера, разработчики бота и участники административных ролей |

Все команды работают только на серверах. `channel` по умолчанию — текущий канал; в опции
можно выбрать текстовый или новостной канал.

### `/embed`

* `color` — HEX (`#5865F2`, `0x5865F2`, `5865F2`, `#F00`) или название: `blurple`, `green`,
  `yellow`, `fuchsia`/`pink`, `red`, `white`, `black`, `dark` (и русские названия).
  Цвет и права проверяются до открытия формы, чтобы ошибка не стоила набранного текста.
* Форма: заголовок, текст (Markdown), баннер, миниатюра, подпись. Нужно заполнить хотя бы
  заголовок, текст или баннер.
* Проверяются лимиты Discord: заголовок 256, текст 4096, подпись 2048, всего 6000 символов;
  ссылки — только абсолютные `http(s)://`.
* При публикации метка времени (если включена) заменяется моментом публикации.

### `/staff`

* «Административная» роль — любая роль хотя бы с одним из прав: администратор, управление
  сервером, ролями, каналами или сообщениями, бан, кик, тайм-аут участников.
* Роли интеграций (в том числе роль самого бота) и роли без прав (вроде «System») не учитываются.
* Группы идут по позиции роли на сервере; участник показывается один раз — под своей высшей
  административной ролью; пустые роли не выводятся.
* Роли с правом «Администратор» помечаются «· полные права».
* Текст никогда не превышает лимит embed: не поместившиеся участники и роли заменяются
  счётчиками «и ещё N».

## 4. Архитектура

Три слоя, зависимости направлены сверху вниз:

```
src/
├── main.rs              точка входа: .env, журнал, код выхода
├── app.rs               запуск: приложение → разработчики → регистрация команд → Gateway → завершение
├── config.rs            переменные окружения (токен, BOT_DEVELOPERS)
├── state.rs             AppState: разработчики, время запуска, ShardManager
├── error.rs             AppError (User | Discord), Fatal (ошибки запуска), Chain (цепочка причин)
│
├── commands.rs          реестр команд (ALL) и тест ограничений Discord на определения
├── commands/            возможности бота — по модулю на команду
│   ├── ping.rs
│   ├── say.rs           команда и форма /say
│   ├── say/
│   │   └── mentions.rs  какие упоминания уведомляют (чистая логика, тесты)
│   ├── embed.rs         команда, форма и кнопки /embed
│   ├── embed/
│   │   ├── color.rs     разбор цвета (чистая логика, тесты)
│   │   └── draft.rs     сборка и валидация embed (чистая логика, тесты)
│   ├── staff.rs         данные /staff из Discord
│   └── staff/
│       └── render.rs    текст /staff в пределах лимитов (чистая логика, тесты)
│
├── framework.rs         инфраструктура взаимодействий; о конкретных командах не знает
└── framework/
    ├── command.rs       трейт SlashCommand, окружение Cx, Registry
    ├── handler.rs       события Gateway: маршрутизация, проверка права, отчёт об ошибках
    ├── caller.rs        вызвавший участник и его права; названия прав по-русски
    ├── custom_id.rs     формат custom_id кнопок и форм
    ├── input.rs         опции команд и поля форм
    └── reply.rs         ответы: эфемерные сообщения, сообщение об ошибке
```

Принципы:

* **`framework` не зависит от `commands`.** Команды передаются в него при запуске через
  `Registry`, поэтому инфраструктуру можно менять и тестировать отдельно от возможностей.
* **Чистая логика отделена от ввода-вывода.** Всё, что можно проверить без Discord (валидация,
  форматирование, разбор), лежит в подмодулях команд и покрыто тестами.
* **Стиль модулей** — `foo.rs` рядом с каталогом `foo/`, без `mod.rs` (закреплено линтом
  `clippy::mod_module_files` в `Cargo.toml`).

### Поток взаимодействия

1. `Handler` находит команду-владельца: слэш-команду по имени, кнопку или форму — по первому
   сегменту `custom_id`. Неизвестное взаимодействие (удалённая команда, форма от старой
   версии) получает ответ «Это действие устарело», а не молчаливый отказ Discord.
2. `Handler` строит `Caller` (сервер, участник, канал) и проверяет право команды.
3. Обработчик получает `Cx` — serenity-контекст, состояние бота и проверенного вызывающего.
   `Cx` реализует `CacheHttp`, поэтому передаётся в методы serenity напрямую.
4. Обработчик возвращает `Result<()>`. При ошибке `Handler` пишет её в журнал и показывает
   пользователю эфемерное сообщение: текст `AppError::User` как есть, для `AppError::Discord` —
   понятное описание по коду Discord (нет доступа, не хватает прав, отклонены данные) или
   общее сообщение.

Обработчики отвечают на взаимодействие последним действием либо сначала вызывают `defer`
(`/ping`, `/staff`). Поэтому `Handler` всегда знает, как сообщить об ошибке: новым ответом или
заменой заглушки «бот думает…».

### Состояние между шагами

`custom_id` имеет вид `<команда>:<действие>[:<аргументы>…]`, например
`embed:modal:<канал>:<цвет>:<метка времени>` и `embed:publish:<канал>`. Состояние диалога
передаётся в нём самом, а embed — в эфемерном предпросмотре. Бот ничего не хранит между
шагами, а открытые формы переживают перезапуск. Аргументы приходят от клиента, поэтому каждый
шаг проверяет их заново, как и права.

### Gateway

* Интенты: только `GUILDS`. Его достаточно для кэша серверов, ролей и каналов.
* Команды регистрируются глобально при запуске, до подключения к Gateway. Это полная
  перезапись: команды, удалённые из кода, исчезают из Discord.

### Как добавить команду

1. Создать `commands/<имя>.rs` с типом, реализующим `SlashCommand`: `name`, `description`,
   при необходимости `options` и `permission`, обязательно `run`; для кнопок и форм —
   `component`/`modal` (их `custom_id` строится через `CustomId::encode(NAME, …)`).
2. Добавить модуль и тип в `commands.rs` (`mod <имя>;` и элемент массива `ALL`).

Регистрация, маршрутизация и проверка права подключатся автоматически; `cargo test` проверит
определение команды на соответствие ограничениям Discord.

## 6. Планы

* **Голосовые комнаты** будут реализованы заново. Их состояние (хабы, канал панели, комнаты) —
  первые данные, которые нужно хранить на диске по серверам: состояние только в памяти теряется
  при перезапуске. Для этого понадобится слой хранения (например, SQLite через `sqlx`) и
  команда настройки для администраторов. Настройки сервера по-прежнему не должны попадать ни
  в код, ни в `.env`.
